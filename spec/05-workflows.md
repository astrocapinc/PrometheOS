# Research workflows

## The daily loop

1. Researcher or coding agent reads a bounded project context: current question, supported findings with conditions, corrections, unresolved questions, adopted actions and coverage limits.
2. Coding agent works in its existing environment. MATLAB/Simulink, shell execution, code editing and debugging remain there.
3. Agent registers selected outputs and an honestly labeled execution receipt, then proposes a notebook entry linked to those versions.
4. PrometheOS validates structure, references, quantities, revisions and authorization. It stores the entry and updates derived views.
5. The next-step view explains candidates in relation to the current state. The researcher adopts, edits or dismisses them; the coding agent resumes from that record.

No model is required for capture, source checking, notebook rendering, corrections, search, task management, backups or reading context. PrometheOS can remain useful during provider failure.

## Notebook and next steps

Default notebook is a deterministic chronological/subject-filtered view of entries with current correction notices and source links. Generated summaries are optional layers with an explicit label, timestamp, input sequence and citations. Original text is one click away. A view may highlight relevant spans; it must not claim that generated wording is a quote. User-authored edits become a new entry revision, not a change to the source.

Context selection prioritizes applied corrections and unresolved contradictions, current objective, recent adopted decisions, evidence tied to that objective, then secondary background. Return the selection policy, included/excluded counts, unavailable roots, stale/missing sources and truncated groups. If critical correction context cannot fit the budget, return a reduced context with a visible incomplete flag; never silently drop the contradiction and keep the attractive result.

Next steps combine deterministic candidates (unowned adopted item, overdue action, unresolved challenge, source missing, paper requirement unknown) with optional external-agent suggestions. Every candidate contains `why_now`, supporting record refs, expected output, dependencies, estimated effort band (small/medium/large/unknown) and what would change the recommendation. No invented exact duration or opaque priority score. Ordering: blocked commitments with remediable blockers, due adopted work, unresolved evidence affecting a current deliverable, then exploratory suggestions. Human priorities can override with a recorded reason.

## Research meetings and hierarchy

Typed meeting capture is available early. Raw audio and recording arrive at CP6. Capture the original notes/media as a version; record attendees only when known. Extraction creates proposed items classified as observation, suggestion, request, decision, commitment or question, with exact supporting locators. Ambiguous ownership/dates stay unknown. A supervisor's tentative remark does not become a task simply because of their role.

Reconciliation shows proposed items beside current actions and their evidence. Exact source+locator re-import is idempotent. Similar topics generate merge candidates but require an explicit choice; distinct operating regimes or paper scopes stay distinct. Adoption can create/update a linked action and its commitment in one transaction. Revising an adopted item invalidates relevant task views, not historical quotes. The system shows the state before and after a meeting using recorded sequences.

Roles capture researcher/supervisor/collaborator/reviewer relationships at project/paper scope with effective dates. This helps explain requests, authorship work and review stages; it is not a multi-user permission platform. Never assume a recorded role determines authorship eligibility.

## Audio and bounded AI

CP6 supports import of common WAV/MP3/M4A inputs after inspecting selected decoders and their licenses. Preserve raw bytes when retention is chosen. Transcripts are derived source versions with timestamp locators and engine/version/language metadata. Long transcription jobs persist chunk offsets, input digest, engine/model configuration and completed segment IDs. Resume only against the same digest/configuration; deduplicate overlapping segments deterministically and require restart on changed inputs. Speakers remain labels unless the researcher maps them. Low-confidence or inaudible spans remain marked; transcription does not establish consent or identity.

First local transcription candidate: an optional faster-whisper adapter, pinned and license-verified at CP6; CPU execution is the supported baseline. Model downloads require an explicit action showing size/license/location. If feasibility fails, document an amendment and select a supported adapter; do not move inference into the mandatory core. Remote transcription is separately opt-in with a preview of transmitted data.

Windows live recording uses a narrow capture adapter: enumerate/select microphone and WASAPI loopback system audio, start/pause/stop/cancel, visible elapsed time/input indicators, device-loss handling and recoverable temporary segments. CP6 begins with a bounded feasibility spike using a maintained capture library or Windows API binding; verify actual microphone and loopback on the target machine before promising online-meeting capture. Library choice is deferred to that measured spike, not the product behavior. No automatic meeting bot, conferencing-account join or hidden capture. Default record button reminds the researcher to establish participant permission under their applicable rules, without inventing jurisdiction-specific advice. File import remains usable if hardware capture is blocked, but R12 stays incomplete.

Provider protocol: `generate(structured_task, filtered_sources, output_schema, budget, cancellation) -> {output, model_id, usage, request_receipt}`. Implement one documented adapter at CP6, plus deterministic fake transport tests; do not claim compatibility with every provider from an “OpenAI-compatible” label. Endpoint and model are explicitly configured, credentials held outside the project. No tools, shell access or recursive model loop. One generation and at most one schema-repair attempt; maximum input/output and attempt count enforced before calls. Unknown remote completion after timeout is not silently repeated. Cost estimates are labeled estimates; billed cost cannot be guaranteed from token limits alone. CP12 (A02) generalises this adapter into the provider capability interface and routing policy below; CP6 acceptance (C06-AI) is unchanged, although shaping the CP6.3 adapter as one implementation of that interface avoids rework. Under A07 the intelligence layer's gateway (CP22) is that generalisation for generation and classification; see The intelligence layer below.

A generation stores its input digests and output provenance, then validates source locators, all structured quantity bindings and purpose schema. Unverifiable claims stay proposals with clear limitations. Model outage shows deterministic content and a retry action; it never hides the notebook. Normal content only leaves through the configured provider by default; restricted/private inputs need a separate explicit egress grant. (A02: this default holds until CP12's settings migration replaces it with an explicit routing policy that keeps an existing provider configuration as remote_allowed for generation through that provider only; see Practical local AI below.)

## MATLAB/Simulink evidence

PrometheOS registers M, SLX, MAT, CSV, figures and logs as sources/artifacts. It can show text, images, PDFs and declared result summaries. It neither renders an SLX workbench nor claims to understand every Simulink model. The external coding agent owns simulation invocation and license/runtime setup.

Use a result receipt with environment, command, inputs, output hashes, success/failure and limitations. For example, a plant simulation without measured validation must retain that fidelity boundary. A numerical improvement in a simplified regime does not silently establish whole-vehicle performance. Synthetic fixtures test those distinctions; the live MATLAB gate requires actual execution outside the fixture suite and comparison of retained output hashes.

## Papers and academic deliverables

Paper workspace connects objective, scoped claims, figures/tables, manuscript versions, target-venue sources, requirements, deadlines, author tasks and reviewer comments. A venue checklist is an importable, dated source-derived artifact, never a guessed universal IEEE checklist. If the venue is unknown, label it unknown. Requirement rows contain exact source/version, applicability, evidence and last check date; a model-generated checklist stays unreviewed.

`paper check` is pure: return missing evidence, contradicted/superseded claims used by anchors, unavailable artifacts, unchecked venue requirements, and unresolved review tasks. It does not score acceptance probability or certify compliance. Saving the report creates a new entry only on request. Manuscript version changes mark unmapped anchors needs_review; attempt deterministic exact matching, then propose a remap for approval. Do not assume line numbers survive edits.

Support local Markdown/LaTeX sources and PDF preview/export bundles. Under A01 the hub also offers a LaTeX workspace (below); without it, compilation remains the coding agent's or researcher's own tool and there is no implicit TeX installation. The coding agent may author/edit/compile using its own tools and register results. Overleaf handoff starts with local/Git import-export plans and clear conflict previews. Live Overleaf writes are part of the A01 workspace (CP9, E07) and each push requires explicit owner authorization; v1 does not build a cloud editor or promise comment/track-change synchronization. Preview drafts in the hub and open the specialist editor only when required.

### LaTeX manuscript workspace (A01, CP9)

The researcher binds a paper to a local LaTeX folder, often an Overleaf Git clone, and edits it in the hub. The editor shows the file tree and outline. It completes references, labels and citation keys, and marks lines bound to anchors with their claims and evidence. Inserting a citation or figure from recorded evidence writes ordinary LaTeX and records the relation. Saving writes the file atomically only if its bytes still match the version the editor loaded; otherwise the editor keeps the draft and shows the external change. Compile runs Tectonic on a staged copy. It returns diagnostics mapped to file and line, and registers PDF, log and SyncTeX outputs as generated versions bound to the exact input versions. Clicking in the PDF opens the source line, and the reverse. A compile failure keeps the previous PDF visibly labelled with its older version.

Overleaf synchronisation uses the Git integration. Pull shows incoming changes and integrates only by fast-forward or a clean merge of non-overlapping changes. A divergent or conflicting history stops with both sides intact and an explanation. Push requires an explicit owner action for the exact commit plan and is never forced. Comments, tracked changes and Overleaf history labels are not synchronised. Manuscript changes arriving by pull or save go through the anchor remap rules above.

Review rounds store comment sources, proposed responses, linked changes and resolution evidence. Submission/acceptance are owner-confirmed events. PrometheOS prepares a reproducible local submission bundle; it never sends it to a journal by default.

## Recurring work

CP7 offers source-refresh checks, paper-readiness checks and project digests. Each run records what changed and why it matters; unchanged runs stay quiet. External literature feeds are optional adapters with source/license/rate limits, not a built-in promise to watch the whole internet. Recurrence runs only while an explicitly started process or user-installed service runs. No claim of unattended execution after the laptop is off. Scheduling is a convenience over bounded handlers, not an agent orchestrator. Literature watches (A02, CP14) are one such handler, tied to a saved inquiry or claim.

## Research continuity (A02, CP10)

A finding is a claim under stated conditions: objective, system, operating regime, comparator, fidelity, validation level and the assumptions it relies on. A negative result for one objective never becomes a verdict on the whole project. Assumptions and constraints are attributed entries that claims and entries point to, so defaults and human constraints stop living in scattered prose. Superseding an assumption is a correction like superseding a claim: an agent may propose it, the owner's decision authority applies it, and the replacement must be another assumption entry. Applying any correction, this one included, flags every dependent claim, action, generated view, matrix row, deliverable and manuscript use for review in the same transaction. Revising an assumption's text also flags its dependents, which are bound to the revision they relied on.

External scientific runs belong to the coding agent and its tools. The agent registers a run (host, command summary, working-root alias, expected outputs) and reports its status; PrometheOS records what was reported and never starts, stops, queues or restarts it. A timeout or silence becomes status unknown, never failure or success. Execution, output capture, interpretation and researcher assessment are four distinct steps. A completed run, or an execution receipt imported without a registration, waits in an awaiting-interpretation queue until an assessment or reviewed entry cites it. Dismissing one is itself a reviewed entry that cites it and gives the reason, so nothing leaves the queue silently. Each artifact shows its availability and backup coverage; a digest is not a backup, and reference-only bytes are never shown as backed up.

Resuming after a closed chat needs no prose handoff. Context and Now are generated from structured state: what changed since the last visit, what is due, what is running, what awaits interpretation, which approvals wait for the owner, and why the next adopted action is next. Workspace and branch coverage stay factual inventory fields.

**The research map (A06.1, CP20).** The record shows each claim's derived status under the question it answers, each question under its deliverable or the objective, and each deliverable's stage with the few things that move it to the next. Anything uncertain (stale, settling, conflicting, unverified, a missing artefact) becomes a proposed verification action with its kind and estimated cost, deduplicated per claim and cause, ordered cheapest first. Read-only checks inside the owner's budget may be started by the agent without a per-item question (spec/04); everything else, and every value judgement (scope, venue, weakening a claim, a long compute budget), reaches the owner as a decision card with what, why, the recommendation and the default. A check records expected, measured and tolerance, so "reproduced" and "changed" are read from the record, not from prose.

## Owned literature workflow (A02)

PrometheOS owns the workflow definitions, schemas, review history and exports; mature libraries do parsing, search and transport. The path from question to report:

1. **Library (CP11).** Import BibTeX, RIS and CSV files, PDFs, or the local Zotero library (read-only, through its local API). Original bytes stay retained source versions. Identifiers (DOI, arXiv, PubMed) are normalised. Exact identifier duplicates resolve to one work keeping all provenance; similarity matches are only proposed for review; preprints and published versions are related, not merged. PDF text is extracted locally into derived versions with page and span locators; OCR, when used, is a derived source beside the original, never a replacement. Works are searchable through FTS5, annotatable and exportable.
2. **Evidence matrix (CP11).** Columns fit the field (methods, conditions or population, comparator, findings, quantities, limitations). Every proposed or reviewed cell binds a work, version, locator and quote digest and records how it was produced and reviewed; a cell without evidence can only be marked unsupported. Invented IDs, bad locators and altered quotations are rejected. Metadata-only, abstract-only, full-text and unavailable states stay visible; an abstract is never presented as a full-text review. Reviewed findings link to claims, open questions and deliverables without silently overwriting accepted decisions.
3. **Discovery and review (CP13).** A saved inquiry holds question, purpose, scope, seed papers and inclusion and exclusion criteria. Queries may be proposed by a local or configured remote model and are always editable. Discovery adapters for selected public scholarly APIs run only after opt-in and a shown plan, which also names the services that will receive the owner's contact email, and persist query, filters, provider, pagination, time and failures, so coverage is visible. Screening by rules, lexical ranking, optional local classifiers or bounded model calls records labels, reasons, reviewer or method and rubric version, including uncertain and insufficient-information outcomes; classifier and model labels stay proposed until a reviewer confirms them. If CP13 lands before CP12, local classifiers are unavailable and a model call runs only through the CP6.3 adapter under its existing explicit configuration and egress preview, or returns capability_unavailable. Legitimately accessible full text is obtained (for example open-access locations) or supplied by the researcher. A cited synthesis is validated against retrieved versions; semantic support remains for review. Exports cover bibliography, screening decisions, matrix, search history and report.
4. **Watches (CP14).** Saved queries refresh incrementally, process only new or changed items, stay quiet when nothing relevant changed, notify when new material may affect a linked question or claim, and pause on quota without repeating completed stages.

A general exploration is not a systematic review. Systematic-review mode requires a saved protocol, inclusion and exclusion records, recall checks and a predefined stopping rule. Ranking never establishes that unseen or excluded papers are irrelevant, a missing result does not prove novelty, and a citation recalled by a model is not retrieved evidence. These pipelines are declared and bounded (spec/07): built-in operations only, with declared inputs, outputs, limits and review points.

## Practical local AI (A02, CP12)

Most repeated work needs exact computation, retrieval and classification rather than a chat model. The policy is: exact computation or rules, then local retrieval or a classifier, then optional compact local generation, then an explicitly allowed remote model. It is not a mandatory cascade: each task uses the cheapest evaluated path that meets its requirements, and a local failure never silently triggers remote egress or a charge. No model, local or remote, is the authority for permissions, arithmetic, deadline ordering, scientific acceptance, novelty or publication readiness; those stay in code or with the researcher, and a model's confidence score is not measured correctness.

A provider capability interface covers generation, embedding, transcription and classification; not every provider offers every capability, and one configured provider should cover the initial remote features. A routing policy per project and workflow is local_only, remote_allowed or manual, and the selected route is always shown. CP12's settings migration writes an explicit policy for every project: an existing CP6.3 provider configuration, which was the owner's egress decision, carries forward as remote_allowed for generation through that provider only, and every other route starts local_only. If this changes how CP6.3 behaves, CP12's impact record lists C06-AI as affected, and it lists the C13 and C15 checks whose model calls it brings under the policy. Each call records provider, model version, workflow or rubric version, input versions, usage and outcome, under per-workflow limits and spend reservations that are estimates, not exact caps.

The local model manager offers the same lifecycle in the app and through MCP and HTTP: list and inspect, preview size, licence, exact revision hash, resource class and location, install explicitly with digest verification and resumable download, import verified files offline, configure per-task selection and limits, show load state and measured memory, cancel, unload, remove and run a bounded benchmark. Downloads are network activity even when inference is local; nothing downloads automatically, and removing a model never deletes sources or decisions.

CPU-first components (chosen and pinned at CP12 after licence and hardware review; candidates in spec/09): SQLite FTS5/BM25 as the baseline, small chunked embeddings and hybrid retrieval that is enabled only if it beats that baseline on labelled questions, a TF-IDF/linear classifier with abstention trained on reviewed labels, page-selective OCR, and local transcription from CP6. Compact generation is optional and off by default until evaluated. Quantitative targets are recorded before measurement and never adjusted after a failure; vendor benchmarks are not PrometheOS results. Offline operation is verified with the network blocked after assets are installed.

## The intelligence layer (A07, CP22)

PrometheOS's own fast models do bounded, typed work that rules cannot settle and that would otherwise wait for an agent session or the owner: classify an adoption family the rules left as competing, propose which question a claim answers, propose an outline from a folder's README lines, word a card's plain text. Each task is registered with a versioned input model, a strict output model with an `abstain` branch, a template, a validator and a declared effect. It runs on rules first, then on the gateway inside the owner's standing policy, or on the coding agent through the existing prepare and submit path. All three executors pass the same validators (D16, A07.3). The result is a proposal with its provenance and evidence tier (T4 for a verified quote, T8 for a hint), never a decision.

- **Trust is measured.** A task is trusted for a model only after its golden set (synthetic first, then the owner's labelled sample, E20) meets the targets of an evaluation record fixed before the first measurement (A07.7: metrics, 95% one-sided Clopper–Pearson bound, minimum size, coverage), measured on replies the gateway itself recorded. Until then its proposals are hints. A trusted proposal may only become a card's recommended answer for a reversible outcome that resolves no competition; moving a family out of `compete` or closing an owner item always takes the owner's answer on that item. Targets are never lowered, and a change of task, template, wire schema, model or served provider set needs a new measurement.
- **Replay.** Model replies are not reproducible even at temperature 0, so every reply is stored with its input digest in its call receipt. Tests and walks run on recorded cassettes and make no model calls; a cassette confers no trust. A cache hit returns the stored proposal; a new sample adds a proposal and never alters a recorded one.
- **What leaves.** Only normal-sensitivity input inside the policy. Files in a bundle are named by root alias and relative path, and a file's sensitivity is the highest of its adoption root's (owner-set; restricted while unset) and of any record citing it.
- **Spend.** The layer reserves against the per-run and monthly caps before each call, reads the key's remaining limit before a batch, and stops cleanly at any cap with finished items kept. A call with an unknown outcome is held, never repeated.
- **Retrieval for linking.** BM25 over FTS5 is fused with local CPU embeddings (exact search; a project's size needs no vector database) and optionally reranked locally, only where the fusion beats BM25 alone on a labelled set, by recall@k in a paired comparison fixed before the first measurement. Results are record ids for linking and proposing; there is no question-answering engine.
- **Without a key.** Every place that would use the layer runs its rules or agent path and says in one line what it did instead.

## Meeting-to-deliverable recipes (A02, CP15)

Advisor agendas, short briefs, claim and do-not-claim cards, slides, speaker notes and reviewer responses are rendered from the same reviewed evidence, adopted actions and review rounds. Each output is an ordinary editable file registered as a generated source that records the evidence versions and template version it used. Superseded, withdrawn or unreviewed evidence is excluded or visibly flagged, and a later correction marks earlier outputs stale. Templates are inert files; optional model drafting goes through the routing policy and is labelled. If CP15 lands before CP12, drafting runs only through the CP6.3 adapter under its existing explicit configuration and egress preview, or returns capability_unavailable; no recipe needs a model. The LaTeX workspace (A01) remains the manuscript editor.

## Optional connectors (A02, CP16)

Connectors save work without making any account required. The local Zotero connector comes first, then a calendar. Each keeps remote IDs and versions or etags, recovers from cursor expiry, applies tombstones, deduplicates and assigns one owner to each synchronised field, surfacing conflicts instead of overwriting. Writing back to an external service uses only an interface verified at CP16 and is otherwise not offered. Disconnecting stops access, keeps permitted local records and shows them as stale. Credentials are entered in the provider's or the OS's interface and stored by reference. Quotas and costs are shown, and unapproved paid expansion is disabled. Connector content is untrusted data. A missing calendar never disables native deadlines, and a missing reference-manager account never disables the imported bibliography.

## Work items and the queue (A05, CP18)

- **Creating work items.** The researcher adds tasks and assignments in the hub (or through any interface), with an optional deadline and a description of what is wanted. Examples: "submit paper P1 to journal X", "group-meeting presentation".
- **Events.** As deadlines approach, and as results, approvals and corrections need attention, events appear in Now and in the queue.
- **Agents ask; they never self-start.** The one exception (A06.1, CP20) is a read-only verification action inside the owner's budget, which the agent may start without a per-item question and reports (spec/04).
  - When the researcher opens an agent session, or asks, the agent reads the queue, summarises it and asks whether to work on an item.
  - It never starts work on its own, and never insists because of a deadline.
  - Work the researcher accepts updates the action, and its completion evidence closes it.

## Adopting an existing folder (A05, CP17)

1. **Choose roots.** The researcher selects a folder and optional exclusions.
2. **Inventory and analysis.** PrometheOS inventories it without writing to it and runs the analyzers of the selected adoption profile.
3. **Review in the hub.** It shows families of related files with a ranked current member, the evidence and contradictions behind each rank, and what it could not read.
4. **The consolidation plan.** Conflicts, re-runs, comparisons and proposals become work items that the coding agent carries out with its own tools and reports back. PrometheOS validates the results against the inventory. From CP20 (A06.1), each family has a class (variant, identical, tool output, run log, history, lineage, succession, compete) from deterministic rules first; only real competition and undecided succession defaults become owner work items, checks the agent can do become verification actions, and the other classes need no item. The scan proposes an outline (tracks, deliverables, questions, results with their producers, stale candidates), each item citing its file and line, which the owner confirms once or corrects. A baseline file can be cited by its scan digest as a reference-only version, shown unverified until a source check confirms its bytes.
5. **Baseline.** The researcher accepts a baseline.
6. **Re-adoption.** Later re-adoption reports what changed and the drift from the baseline.
7. **Exports.** Exports include a one-way fenced Markdown export for a notes vault. Deleting or deduplicating files is only ever proposed.
