# Records, evidence and state

This is the normative logical model. CP0 turns the contracts introduced at that checkpoint into Pydantic models and exported JSON Schemas; later checkpoints add their specified records. Do not create speculative empty tables. All public models reject unknown fields. Use JSON-compatible values, UTC RFC3339 timestamps and finite numbers. Decimal quantities use strings, never binary floats as authoritative scientific text.

## Identity and revisions

Identifiers are `<kind>_<UUID4>` with canonical lowercase hyphenated UUIDs, e.g. `entry_00000000-0000-4000-8000-000000000001` in fixtures. Allowed kinds are project, source, version, entry, claim, assessment, correction, person, role, meeting, item, action, paper, anchor, task, job, package, run. A02 adds execution (CP10), work, matrix and extraction (CP11), and inquiry, search and screening (CP13), each at its checkpoint (see the mapping below). Clients may preallocate IDs to reference earlier creates in the same transaction. IDs are unique within a project; a relation may not cross projects.

Every record envelope contains `id`, `kind`, `rev` (positive integer), `recorded_at` (server clock), `occurred_at` (nullable), `sensitivity` (`normal|restricted|private`), `lifecycle` (`active|archived|deleted`) and `body` (typed below). Creates use `base_rev=0`; updates require the exact current revision. All string lists have explicit schema length limits. Default title limit 300 characters, free text 64 KiB, reference lists 200 items. Larger text is a source payload, not an oversized property.

`recorded_at` is when the system learned something. `occurred_at` is an asserted event time. As-known queries use the committed project sequence; late-entered meetings never rewrite what was known earlier. Clock order is not causality. Historical revision views exclude physically purged bodies and say so.

Common references are `{id, rev}`. Evidence references are `{source_id, version_id, locator, quote_sha256}`; `locator` is one of text (line range), PDF (page and optional bounding box), audio (start/end milliseconds), or JSON (RFC6901 pointer); under A06.1 also `file`, a whole-artefact reference bound by the version digest with no quote and no quantity, for binary artefacts such as `.mat`, `.slx` or `.png`, rendered with its path, digest and size. Quotes, if retained, must match the referenced retained version. A digest of an unavailable external source is identity metadata, not an accessible quotation.

Init requires a title and objective; the objective may honestly say undecided. Settings updates are revisioned protected project mutations through the shared transaction service. Never infer timezone, legal jurisdiction, institution or publication rights from a username or file path.

## Transitions and protected decisions

Normal entries and observations can be created by an authorized agent. Imported text is data, never a control instruction. Agents may propose claims, corrections, meeting actions and plans. All routes (create, revise, transition, relation, import and task submit) enforce the same effect-based policy. Creating a record directly in a protected state is not a bypass. Raw relations are descriptive and cannot apply a correction or promote scientific state. Applying a correction, adopting a commitment, changing a claim to supported, declaring a paper submitted/accepted and expanding data egress require a valid decision capability under the interface policy. A supplied `author_ref` or `method=researcher` does not grant authority.

Claim support requires at least one supporting assessment with scope_match=true and accessible evidence. It means support within recorded conditions, not proof. Challenges retain both sides; automatic conflict detection may flag `needs_review` in derived views but must not silently decide the outcome. Supersession requires a replacement; correction targets/replacements must not form cycles. Apply the correction and invalidate dependent views/anchors in one transaction. No automatic replacement of original source text.

Action transitions: proposed→ready/cancelled; ready→in_progress/blocked/cancelled; in_progress→done/blocked/ready/cancelled; blocked→ready/cancelled; done→ready only with a recorded reopening reason; cancelled→proposed only with reason. `done` needs completion evidence or a capability-approved explanatory note, not a model assertion alone. Dependencies must be done before ready unless an explicit recorded waiver is approved. Missing owner is visible, not assigned to the founder automatically.

Meeting suggestions remain proposed unless adopted. Roles explain who requested work; they never mean every supervisor remark is a commitment. Paper status transitions follow the table order except withdrawal and explicit backward moves with a reason. Submission status is a recorded external event; PrometheOS does not submit.

## Source checks and scientific quantities

Store source-check observations separately from immutable versions: `{version_id, checked_at, retained_digest_ok, origin_current_digest, origin_reachable, error}`. A changed current file does not invalidate an intact historical version. A missing reference-only file prevents verification and quote generation. Never silently rebind a citation to new bytes.

Structured quantities are `{decimal, unit, source_ref, source_pointer}`; under A06.1 a binding may also carry `name` (the quantity's label or macro, at most 80 characters) and `definition` (at most 300 characters), and a claim may carry its own `quantities[]`. A summary's numbers must each equal a bound quantity of its claim, and a whole-artefact `file` locator never binds a quantity. Render decimal and unit verbatim from the binding; any conversion must create an explicit deterministic transformation with input, formula, units and result. Validate **every** claimed numeric result, including numbers below ten. No percentage tolerance for copied results. In ordinary prose, dates/section labels are not scientific quantities, but heuristic recognition must not advertise complete numeric verification. Unbound generated numeric assertions fail validation and remain proposals.

Execution receipts are evidence sources with `origin=agent_receipt`: reported command, working-root alias, environment, exit status, output hashes and `observation=reported|observed`. Importing an external agent's receipt never upgrades it to observed. No claim that MATLAB ran from a fixture or textual receipt. Reported execution, integrity of bytes, human approval and scientific validity are four different properties.

## Derived knowledge

Relations index citations, claim support/challenge, correction, dependencies and manuscript use. Compute affected closure for an applied correction; source history stays intact. Derived context/notebook views carry `project_seq`, source bindings, filters, generation method and coverage limitations. Generated views can be discarded and rebuilt; approved entries retain their version history.

Under A06.1 relations also record the research map: `answers` (claim to question entry), `addresses` (question to paper, or to the objective entry) and `draws_on` (claim or question to a `track` entry). They are descriptive and promote nothing.

**Producer edges (A06.1).** A version's producers are the `input_refs` of the execution receipt whose `outputs` contain it, and, where an adoption scan found a producer relation between two files (`generated_by`, `used`), the ledger versions whose sha256 equals those files' scan digests. Nothing else counts as a producer.

**Derived claim status (A06.1).** Derived views give each claim one status, with all its causes, by this precedence:

1. `withdrawn` and `superseded`: the claim's own state.
2. `stale`: a producer of an evidence version has a newer retained or observed version than that evidence; or the evidence's run predates an applied correction or an assumption revision the claim `depends_on`; or a source check found the origin changed.
3. `conflicting`: two quantity bindings of the claim, or of entries listing it in `claim_refs`, have the same `name` and the same `definition` (or both none) and different decimal or unit; bindings with different definitions are never a conflict.
4. `settling`: a proposed correction targets the claim, or a decision card about it waits for the owner or its default date.
5. `unverified`: no assessment cites it, or no evidence leaf resolves.
6. `corrected`: an applied correction superseded the claim's statement or a bound quantity, and the replacement has a supporting assessment.
7. `holds`: a supporting assessment with `scope_match` and evidence at current digests.

`holds` and `corrected` carry their basis, decided by who recorded it and never by the caller-supplied `method`: `reviewed` (an assessment recorded under owner scope, or the protected claim state), `deterministic` (a check PrometheOS itself ran and recorded) or `agent_reported` (every assessment an agent submitted, whatever its `method`); the last is always shown as such. The status is a rebuildable view flag, never a claim state, and never promotes one. Deliverable stages are derived the same way: framed (the paper has questions), evidence mapped (every claim answering them has resolvable evidence), verified (every such claim holds or is corrected, with the agent-reported ones listed for the owner to confirm), then the paper's own status. A stale, superseded or withdrawn claim is never offered as usable in a paper.

No graph database is required. Knowledge navigation is a filtered list with links/backlinks and a small optional local relationship view. Similar titles are search candidates, never deduplication authority. Exact duplicate imports use digest + source ID + locator + transformation version; two sources with the same text may still be distinct provenance.

## Typed auxiliary payloads

These are deliberately small additions to the preceding closed models, not untyped extension bags.

- **Correction effect:** `{target_ref, effect: withdraw|contest|supersede|replace_text, replacement_ref nullable, replacement_text nullable}`. Supersede requires a replacement claim with its own scope/evidence; narrowing a claim creates that replacement rather than editing its historical scope invisibly. Replace_text is allowed only for entry/item explanatory text, not original source bytes; it requires replacement_text. Target refs bind exact base revisions. Apply checks every target and replacement still matches, applies the requested effects, marks correction applied, and invalidates dependent views/anchors in one transaction. Create corrections only as proposed; applied/rejected transitions use dedicated policy. If any target changed, refresh/review the entire proposal. Preview and approval bind the complete effect list digest. From CP10 (A02), `supersede` also applies to an entry of category `assumption`, and its replacement must be another `assumption` entry. It needs the same decision authority as superseding a claim, sets the target's protected `superseded_by` and flags dependents through the same closure. No other entry can be superseded.
- **Transformation provenance:** `{type: extraction|transcription|conversion, engine, engine_version, model nullable, language nullable, parameters_digest, input_version_refs[], run_id nullable}`. Transcript payload v1 is `{schema_version:1, segments:[{id,start_ms,end_ms,text,speaker_label nullable,confidence nullable,uncertain:boolean}]}`; segment IDs stable within the immutable output. Partial processing state lives in a resumable local processing-job table, not the immutable source bytes. Completion creates a new transcript source version. Availability/extraction fields on version responses are computed from separately revisioned observations; immutable source identity (digest, length, storage binding, capture time, provenance) cannot be revised in place.
- **Execution receipt payload v1:** `{schema_version:1, observation:reported|observed, reporter, command, working_root_alias, started_at nullable, ended_at nullable, environment:[{name,value}], exit_code nullable, input_refs[], outputs:[{source_id,version_id,sha256}], stdout_version_id nullable, stderr_version_id nullable, limitations[]}`. This is a typed source payload; it is distinct from development checkpoint receipts. Secret-bearing environment fields are rejected/redacted at ingestion. Observed is allowed only for an app-controlled verified observer, never an arbitrary imported agent payload.
- **Review round:** stored within a paper body as `{id,label,source_refs[],received_at nullable,items:[{id,comment_source_ref,text,response_text,change_refs[],status:open|drafted|resolved,resolution_evidence[]}]}`. Revisions preserve earlier rounds. A resolved item requires linked change/evidence or an owner-approved rationale; “response drafted” alone is not resolution. Contribution/overlap table is derived from paper contribution, claim refs and related_papers; similarity proposes overlap, never adjudicates plagiarism or publication eligibility.
- **Recipe run record (`kind=run`):** `{package_ref,package_digest,recipe_id,inputs,input_digest,steps:[{id,status:pending|in_progress|blocked|done|skipped,artifact_refs[],check_results:[{id,result:pass|fail|unknown,evidence[]}],reason nullable}],status:planned|active|blocked|completed|cancelled}`. `workflow start` creates it and `workflow step` submits full validated revisions through apply. Completion requires mandatory outputs/checks and no unresolved step; skipped steps need a reason and recipe permission. Records describe host-reported work, not an execution engine.

Operational plans, capabilities, requests, source observations, transcription progress and scheduler leases have dedicated typed tables; their schema is introduced with the feature and exported for contract checks. Lease heartbeats/cache refresh do not advance the research project sequence; changes to research-visible observations/results do. They cannot mutate scientific records outside the transaction boundary.

### A02 schema migrations

Store schema versions are numbered in merge order. The store is at schema 5 under spec 1.1.0, and CP6 or CP9 may add versions first. Each migration is forward-only, tested from the previous supported schema and preceded by a verified backup. Exact columns are fixed in the checkpoint's first task, exported as contracts and reviewed there. Changing a meaning stated here needs an amendment.

- **CP10:** (a) an `operation_runs` table; (b) an `approval_requests` table; (c) a metadata-only `backup_inventory` table; (d) contract additions: kind `execution`, entry category `assumption`, nullable claim `scope.objective`, relation pairs for assumptions and for entries and assessments citing an execution, the correction effect `supersede` on `assumption` entries with a replacement assumption and a protected nullable `superseded_by` on those entries, and error codes `approval_required` and `capability_unavailable`; (e) per-user registry changes: a record of a quarantined damaged store and its replacement after recovery, and a `maintenance_approvals` table for protected maintenance requests raised while no project database is open: recovery registry switches and schema migrations of a store that needs migration (spec/04; A03). Switch rows bind a verified backup and a new store; migrate rows bind from/to schema versions and have no backup or target-store binding. Every migration still creates and verifies its pre-migration backup before changing the store.
- **CP11:** (f) kinds `work`, `matrix` and `extraction`, relation `version_of`, source origin `adapter` for content read through a declared adapter; (g) rebuildable derived tables: a normalised identifier index and FTS coverage of work metadata and extracted text.
- **CP12:** (h) a per-user model registry under the PrometheOS home; (i) a provider usage ledger and the project setting `routing_policy`. The migration writes an explicit policy for every project: an existing CP6.3 provider configuration, which was the owner's own egress decision, carries forward as remote_allowed for generation through that provider only, and every other route is local_only. It grants no new remote permission, and the hub shows the migrated policy; (j) a rebuildable embedding cache outside the authority database.
- **CP13:** (k) kinds `inquiry`, `search` and `screening`. The owner contact email and its owner-approved list of receiving services (initially Crossref and Unpaywall) form a per-user setting outside project stores. Package sidecars gain `pipelines[]` (spec/07).
- **CP14:** (l) job handler `literature_watch` and a `watch_state` table (cursor, seen-item digests, quota pause).
- **CP15:** (m) source origin `generated` and transformation type `rendering` with template provenance.
- **CP16:** (n) `connections` and `connector_items` tables: credential reference, field ownership, cursor, remote ID and version, tombstone, local record.
- **CP17 (A05):** (o) adoption tables outside the record kinds: scan generations, inventory rows (path, stat, content and normalised-text digests, container type, placeholder state), analyzer evidence with tier and analyzer version, families and ranks with reasons, consolidation plans and their versions, and accepted baselines bound to a scan generation. Adopted files are referenced as source versions only when a plan step or the owner selects them; nothing is written into the adopted folder.
- **CP18 (A05):** (p) an `events` outbox written in the same transaction as the change it reports: `event_id`, `type`, `subject_ref`, `occurred_at`, typed `data`, `acknowledged_at` nullable; events are acknowledged, never silently deleted, and purge follows the record purge rules; (q) a `detector_state` table so built-in detectors fire once per condition across restarts; (r) the optional action fields `description` and `labels[]` (additive; stored actions are not rewritten).
- **CP19 (A05):** none in project stores; the desktop application keeps its window and tray settings in the per-user PrometheOS home.
- **CP21 (A07):** none in project stores. The per-user home gains the instance lock file and its advisory metadata, the fixed port, the home's host name (`h` followed by the first 16 hexadecimal characters of the home's UUID: a stable, non-secret DNS label), and the remembered-device credentials (stored as digests, each with its creation time, last use, absolute expiry and revocation).
- **CP22 (A07):** (s) a rebuildable `ai_results` table outside the record kinds, keyed by task kind, task version, template digest, wire-schema digest, model, request parameters, input digest and sample index, holding the validated output, its validation outcome and its call receipt; it is never authoritative and rebuilds from the call receipts, which retain the reply body with the highest sensitivity of the call's inputs; (t) nullable columns on the provider call records for the served model, the served provider, the billed cost and the data policy sent; (u) the standing policy as a new revision of the provider settings: task kinds, sensitivity ceiling, evaluated models, data policy, monthly (per home) and per-run caps, whether agents may start runs, its digest, the provider configuration revision it is bound to, granted by and when; (v) an owner-set sensitivity per adoption root, read as restricted while unset, lowered only by a protected owner decision bound to the alias and its resolved folder, and restricted again when the alias is pointed at another folder; a file's effective sensitivity is the highest of its root's and of any record citing it; (w) the input bundle digest on each call record; (x) in the per-user home, the home's monthly cap and a home-level spend ledger whose reservations are taken under a home lock across projects. The existing CP6.3 configuration carries forward unchanged and grants nothing new. Accepted proposals carry their provenance (task, version, template digest, served model and provider, receipt) in the proposal they create; no existing record kind changes meaning.
